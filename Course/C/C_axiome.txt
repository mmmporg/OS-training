================================================================================
AXIOMES DU LANGAGE C
================================================================================

Ce document répertorie les axiomes, principes fondamentaux et règles immuables
du langage C, basés sur les standards ISO/IEC 9899 (C89 à C23).

Les axiomes sont organisés en plusieurs catégories :
- AXIOMES FONDAMENTAUX : Vérités immuables du langage
- REGLES DU STANDARD : Spécifications techniques du standard C
- CONCEPTS CLÉS : Notions essentielles pour maîtriser le C
- BONNES PRATIQUES : Recommandations pour écrire un code robuste

================================================================================
PARTIE 1 : AXIOMES FONDAMENTAUX DU LANGAGE C
================================================================================

AXIOME C1 : LE PROGRAMME EST UNE COLLECTION DE FONCTIONS
--------------------------------------------------------
Principe : Tout programme C est composé de fonctions. La fonction main() est
l'entrée obligatoire du programme en mode hosted.

Corollaires :
- Chaque fonction a un type de retour et une liste de paramètres
- Une fonction ne peut être définie qu'une seule fois (mais peut être déclarée
  plusieurs fois via des prototypes)
- Le programme est exécuté séquentiellement, instruction par instruction

Exemple :
int main(void) {
    return 0;
}

AXIOME C2 : LE TYPAGE STATIQUE ET MANIFESTE
-------------------------------------------
Principe : Toutes les variables doivent être déclarées avec leur type avant
d'être utilisées. Le type est vérifié à la compilation.

Corollaires :
- Le type détermine la taille en mémoire et les opérations autorisées
- Les conversions implicites sont limitées (promotion arithmétique)
- Les conversions explicites nécessitent un cast
- C est un langage à typage faible (des conversions implicites sont autorisées)

Exemple :
int x = 42;           // Déclaration avec initialisation
double y = (double)x; // Conversion explicite

AXIOME C3 : LES POINTEURS SONT DES ADRESSES MEMOIRE
---------------------------------------------------
Principe : Un pointeur contient l'adresse mémoire d'un objet. Il permet
d'accéder indirectement à des données.

Corollaires :
- sizeof(void*) peut différer de sizeof(int)
- Un pointeur non initialisé (wild pointer) est dangereux
- Le pointeur NULL (0) ne pointe vers rien
- L'arithmétique de pointeurs dépend du type pointé

Exemple :
int arr[5] = {1, 2, 3, 4, 5};
int *ptr = arr;      // ptr pointe vers arr[0]
*(ptr + 2) = 30;     // Modifie arr[2]

AXIOME C4 : PAS DE GESTION AUTOMATIQUE DE LA MEMOIRE
-----------------------------------------------------
Principe : Le programmeur est responsable de toute allocation et libération
de mémoire dynamique.

Corollaires :
- malloc() alloue de la mémoire (non initialisée)
- calloc() alloue et initialise à zéro
- free() libère la mémoire allouée dynamiquement
- Un "memory leak" se produit si free() n'est pas appelée
- "Double free" et "use after free" sont des erreurs graves

Exemple :
int *buffer = malloc(100 * sizeof(int));
if (buffer == NULL) {
    // Gérer l'erreur d'allocation
}
// Utiliser buffer...
free(buffer);
buffer = NULL; // Bonne pratique

AXIOME C5 : LE MODELE MEMOIRE DE C
----------------------------------
Principe : La mémoire d'un programme C est organisée en plusieurs segments :
.text (code), .rodata (données constantes), .data (données initialisées),
.bss (données non initialisées), pile (stack), tas (heap).

Corollaires :
- Les variables globales sont initialisées à zéro (segment .bss)
- Les variables locales non initialisées contiennent des valeurs indéfinies
- La pile pousse vers les adresses basses
- Le tas pousse vers les adresses hautes

AXIOME C6 : LE COMPORTEMENT INDEFINIE (UNDEFINED BEHAVIOR - UB)
---------------------------------------------------------------
Principe : Certaines opérations en C sont définies comme "comportement indéfini"
par le standard. Le compilateur n'a aucune obligation de gérer ces cas.

Exemples de comportements indéfinis :
- Déreferencer un pointeur NULL
- Accéder à un tableau hors limites
- Diviser par zéro
- Utiliser une variable non initialisée
- Overflow d'un type entier signé
- Modifier une valeur const
- Appeler une fonction avec le mauvais nombre/types d'arguments
- Violation de la règle du strict aliasing
- Expression avec plusieurs accès à la même variable modifiée sans point de séquence

Corollaires :
- Le comportement indéfini peut causer n'importe quoi (crash, données corrompues,
  comportement correct par hasard)
- Les optimisations du compilateur peuvent exploiter le comportement indéfini
- Aucune garantie de portabilité pour le comportement indéfini

AXIOME C7 : LA REGLE AS-IF
--------------------------
Principe : Le compilateur peut effectuer n'importe quelle optimisation,
pourvu que le comportement observable du programme soit préservé.

Comportements observables (selon le standard C) :
1. Accès à des objets volatile (strictement selon les règles de l'abstraction)
2. État des fichiers à la terminaison du programme
3. Entrée/sortie sur des dispositifs interactifs (prompt avant attente d'entrée)

Corollaires :
- Le compilateur peut réordonner, éliminer ou fusionner des instructions
- Les variables non utilisées peuvent être optimisées
- L'UB permet au compilateur de faire n'importe quoi car il n'y a pas de
  comportement observable à préserver

AXIOME C8 : LE PREPROCESSEUR EST UN OUTIL DE TEXTE
--------------------------------------------------
Principe : Le préprocesseur exécute des substitutions textuelles avant la
compilation. Il ne comprend pas la syntaxe C.

Corollaires :
- Les directives commencent par '#'
- #define effectue une substitution simple (macro)
- #include insère le contenu d'un fichier
- Les macros ne sont pas typées
- Les parenthèses sont essentielles dans les macros pour éviter les erreurs

Exemple :
#define MAX(a, b) ((a) > (b) ? (a) : (b))
#define SQUARE(x) ((x) * (x))

AXIOME C9 : LES TABLEAUX SE DEGRADENT EN POINTEURS
--------------------------------------------------
Principe : Un nom de tableau se dégrade automatiquement en pointeur vers son
premier élément dans la plupart des contextes.

Contextes où le dégradation NE SE PRODUIT PAS :
- sizeof(arr) : retourne la taille totale du tableau
- &arr : retourne l'adresse du tableau (type pointeur vers tableau)
- arr dans une déclaration de fonction paramètre (mais c'est une spécification)

Corollaires :
- arr[i] est équivalent à *(arr + i)
- sizeof(ptr) retourne la taille du pointeur
- Un tableau ne peut pas être affecté directement (arr = autre_arr est illégal)

Exemple :
int arr[5];
int *p = arr;      // OK, arr se dégrade en pointeur
p = &arr[0];       // Même chose

AXIOME C10 : PASSAGE PAR VALEUR
--------------------------------
Principe : Tous les arguments sont passés par valeur en C.

Corollaires :
- Pour modifier une variable passée à une fonction, il faut utiliser un pointeur
- Les tableaux sont passés par référence (via dégradation en pointeur)
- Les structures grandes sont coûteuses à passer par valeur

Exemple :
void swap(int *a, int *b) {
    int temp = *a;
    *a = *b;
    *b = temp;
}

================================================================================
PARTIE 2 : REGLES DU STANDARD C
================================================================================

REGLE S1 : STRICT ALIASING RULE (C99 6.5p7)
--------------------------------------------
Principe : Un objet ne peut être lu que via un pointeur de son type, d'un type
signed/unsigned correspondant, d'un type void*, ou d'un type agrégat/union
contenant l'un de ces types.

Exceptions autorisées (lues via différents types) :
1. Type compatible avec le type déclaré de l'objet
2. Type compatible avec le type déclaré, mais avec different signedness
3. Type qui est une version signée ou non signée du type déclaré
4. Type void*
5. Type structure ou union contenant l'un des types ci-dessus (inclusivement)

Exemples de violation (UB) :
int x = 42;
float *fp = (float*)&x;
float f = *fp; // VIOLATION ! Lire un int via un pointeur float

Exemple conforme :
int x = 42;
unsigned int *up = (unsigned int*)&x;
unsigned int u = *up; // OK (signed/unsigned correspondant)

Importance pour OSDev :
- Accès à la mémoire VGA via pointeurs char* est OK (void* compatible)
- Accès à des registres via des unions est OK (exception 5)
- Cast entre pointeurs de types différents pour l'accès mémoire est UB

REGLE S2 : POINTS DE SEQUENCE / SEQUENCED-BEFORE (C11)
------------------------------------------------------
Principe : C11 a remplacé les "sequence points" par le modèle "sequenced-before"
qui définit l'ordre d'évaluation.

Règles clés :
- Dans une expression a && b, a est évaluée avant b (évaluation paresseuse)
- Dans une expression a || b, a est évaluée avant b (évaluation paresseuse)
- Dans une expression a ? b : c, a est évaluée avant b ou c
- Dans une expression a , b, a est évaluée avant b
- L'évaluation d'un argument de fonction n'est pas séquencée par rapport aux
  autres arguments
- L'accès à une variable modifiée plusieurs fois dans une expression sans
  point de séquence est UB

Exemples d'UB :
int i = 1;
int j = i++ + ++i;   // UB : i modifié deux fois sans point de séquence
int k = ++i * i++;   // UB : même raison
printf("%d %d", i++, ++i); // UB : arguments non séquencés

Exemples conformes :
int i = 1;
int j = i++;         // OK : une seule modification
int k = (i++) + 1;   // OK : séquence point implicite
int l = i++ , ++i;   // OK : virgule est un point de séquence

REGLE S3 : EFFECTIVE TYPE
-------------------------
Principe : Un objet alloué dynamiquement n'a pas de type déclaré. Son "effective
type" est déterminé par les opérations d'écriture effectuées sur lui.

Règles :
- Lorsqu'un objet est écrit pour la première fois, son effective type devient
  le type du lvalue utilisé pour l'écriture
- Si un objet est réécrit avec un type compatible avec son effective type,
  son effective type peut changer
- La lecture doit respecter la règle du strict aliasing par rapport à l'effective
  type

Exemple :
void *p = malloc(sizeof(int));
int *ip = (int*)p;
*ip = 42;            // effective type de *p devient int
float *fp = (float*)p;
*fp = 3.14;          // effective type devient float (compatible via void*)
int val = *ip;       // UB ! Lecture via int* d'un objet de effective type float

REGLE S4 : TRAP REPRESENTATIONS
-------------------------------
Principe : Certaines représentations bit des types ne correspondent à aucune
valeur valide. Ces représentations sont appelées "trap representations".

Exemples :
- Pour les types à virgule flottante : NaN, infini peuvent être des trap
  representations (dépend de l'implémentation)
- Pour les types entiers signés : la représentation avec tous les bits à 1
  (pour les types à complément à deux) est une valeur valide (-1), mais pour
  les autres représentations (ones' complement, sign-magnitude), ce peut être
  un trap representation (valeur -0)

Corollaires :
- Accéder à une trap representation est UB
- Les variables automatiques non initialisées peuvent contenir des trap
  representations
- memset() avec 0 produit toujours une représentation valide pour les types
  scalaires

REGLE S5 : RESTRICT
-------------------
Principe : Le qualificateur restrict indique au compilateur qu'un pointeur est
la seule référence à l'objet pointé dans sa portée.

Corollaires :
- Permet au compilateur d'effectuer des optimisations plus agressives
- Violation : si deux pointeurs restrict pointent vers le même objet
- Utilisé principalement pour les fonctions de la bibliothèque standard
  (memcpy, memset, etc.)

Exemple :
void copy(int *restrict dest, const int *restrict src, size_t n) {
    // Compilateur peut optimiser car dest et src ne se chevauchent pas
    for (size_t i = 0; i < n; i++) {
        dest[i] = src[i];
    }
}

REGLE S6 : DEFAULT ARGUMENT PROMOTIONS
---------------------------------------
Principe : Lorsqu'une fonction est appelée sans prototype ou avec un prototype
qui ne spécifie pas les types des paramètres (void f()), les arguments subissent
des promotions par défaut.

Promotions :
- float → double
- char, short, signed char, unsigned char, unsigned short → int
- Si int ne peut pas contenir la valeur, promotion vers unsigned int

Exemple :
void f();           // Prototype sans paramètres spécifiés
char c = 'a';
f(c);               // c est promu en int
float f = 3.14;
f(f);               // f est promu en double

Note : Depuis C11, void f() est obsolète et équivaut à void f(void) dans
le contexte de la définition.

REGLE S7 : LIFETIME DES OBJETS
------------------------------
Principe : La durée de vie d'un objet dépend de son mode d'allocation.

Règles :
1. Variables automatiques (locales) : vie limitée à la portée où elles sont
   déclarées
2. Variables statiques : vie durant toute l'exécution
3. Variables globales : vie durant toute l'exécution
4. Objets alloués dynamiquement : vie jusqu'à free()
5. Compound literals : vie limitée à la portée où ils sont créés (sauf si
   static)

Exemple de compound literal :
struct point { int x; int y; };
struct point *p = &(struct point){1, 2}; // Vie limitée à la portée
static struct point *q = &(struct point){3, 4}; // Vie durant toute l'exécution

REGLE S8 : FLEXIBLE ARRAY MEMBERS (C99)
---------------------------------------
Principe : Une structure peut avoir un membre final de type tableau de taille
incomplète (sans taille spécifiée).

Règles :
- Le membre flexible doit être le dernier membre de la structure
- sizeof(struct) ne comprend pas la taille du membre flexible
- L'allocation doit réserver de la mémoire supplémentaire pour le membre flexible

Exemple :
struct buffer {
    size_t size;
    char data[];  // Flexible array member
};

struct buffer *buf = malloc(sizeof(struct buffer) + 100);
buf->size = 100;
strcpy(buf->data, "hello");

PARTIE 3 : CONCEPTS CLES DU C
================================================================================

CONCEPT 1 : ALIGNEMENT DES DONNEES
----------------------------------
Principe : Chaque type a un alignement requis (multiple de sa taille).
Les objets doivent être stockés à des adresses multiples de leur alignement.

Corollaires :
- sizeof(struct) peut être supérieur à la somme des sizeof de ses champs
- __attribute__((packed)) peut supprimer l'alignement (mode freestanding)
- L'accès non aligné peut causer un crash sur certains architectures (SPARC,
  MIPS) ou être plus lent (x86)

Exemple :
struct s {
    char c;   // 1 octet
    int i;    // 4 octets (aligné sur 4)
};
// sizeof(struct s) = 8 (3 octets de padding entre c et i)

CONCEPT 2 : PORTÉE DES IDENTIFIANTS
-----------------------------------
Principe : L'accès à un identifiant est limité à sa portée.

Types de portée :
- Portée de bloc : entre { et }
- Portée de fichier : depuis la déclaration jusqu'à la fin du fichier
- Portée de fonction : paramètres et variables locales
- Les identifiants peuvent masquer des identifiants de portée plus large

CONCEPT 3 : LIAISON DES SYMBOLES
--------------------------------
Principe : La liaison détermine la visibilité d'un symbole entre les fichiers.

Types de liaison :
- Liaison externe (par défaut) : symbole visible dans tous les fichiers
- Liaison interne (static) : symbole visible uniquement dans le fichier
- Une définition externe peut avoir une ou plusieurs déclarations
- Plusieurs définitions externes du même symbole sont interdites

CONCEPT 4 : PRECEDENCE ET ASSOCIATIVITE
---------------------------------------
Principe : Les opérateurs ont une priorité (précédence) et une associativité
qui déterminent l'ordre d'évaluation.

Exemples :
- * (déférencement) a une précedence plus haute que +
- = est associatif à droite (a = b = c → a = (b = c))
- && et || effectuent une évaluation paresseuse
- Les parenthèses peuvent modifier l'ordre d'évaluation

Exemple :
int x = 3 + 4 * 2;   // x = 11 (pas 14)
int y = (3 + 4) * 2; // y = 14

CONCEPT 5 : PROMOTIONS ARITHMETIQUES
------------------------------------
Principe : Les types petits (char, short) sont promus en int avant toute
opération arithmétique.

Corollaires :
- char + char → int + int → int
- short * short → int * int → int
- La promotion préserve la valeur (signée ou non)

Exemple :
char a = 0xFF, b = 0xFF;
int c = a + b;  // c = 0x1FE (pas 0xFE)

CONCEPT 6 : CONVERSIONS DE TYPE
-------------------------------
Principe : Les conversions entre types peuvent être implicites ou explicites.

Regles :
- Conversion implicite : double → float (perte de précision)
- Conversion explicite : (int)3.14 → 3
- Les conversions vers un type plus petit peuvent trancher
- Les conversions de pointeurs sont souvent des comportements indéfinis

CONCEPT 7 : ASSEMBLEUR INLINE
------------------------------
Principe : L'assembleur inline permet d'insérer du code assembleur directement
dans le code C.

Syntaxe GCC :
asm volatile ("instruction" : outputs : inputs : clobbers);

Exemples pour OSDev :
static inline uint8_t inb(uint16_t port) {
    uint8_t ret;
    asm volatile ("inb %1, %0" : "=a"(ret) : "Nd"(port));
    return ret;
}

static inline void outb(uint16_t port, uint8_t val) {
    asm volatile ("outb %0, %1" : : "a"(val), "Nd"(port));
}

CONCEPT 8 : ATTRIBUTS GCC
--------------------------
Principe : Les attributs GCC permettent de contrôler le comportement du
compilateur pour le code système.

Attributs utiles pour OSDev :
- __attribute__((packed)) : suppression de l'alignement
- __attribute__((aligned(n))) : alignement spécifique
- __attribute__((noreturn)) : fonction ne retourne pas
- __attribute__((section(".nom"))) : placement dans une section spécifique
- __attribute__((weak)) : définition faible (peut être remplacée)
- __attribute__((always_inline)) : force l'inlining

PARTIE 4 : AXIOMES DU MODE FREESTANDING (OSDEV)
================================================================================

AXIOME FS1 : PAS DE BIBLIOTHEQUE STANDARD
-----------------------------------------
Principe : En mode freestanding, aucune fonction de la bibliothèque standard
n'est disponible.

Corollaires :
- Aucun printf(), scanf(), malloc(), free()
- Aucun stdio.h, stdlib.h, string.h
- Il faut implémenter soi-même les fonctions de base
- Utiliser -ffreestanding et -nostdlib lors de la compilation

AXIOME FS2 : ENTRÉE DU PROGRAMME
--------------------------------
Principe : En mode freestanding, l'entrée du programme n'est pas nécessairement
main().

Corollaires :
- L'entrée est définie par le linker script (généralement _start)
- Il faut initialiser la pile manuellement
- Aucun environnement n'est fourni (pas d'argc, argv, environ)

AXIOME FS3 : ACCÈS DIRECT À LA MEMOIRE
--------------------------------------
Principe : En mode freestanding, le programme peut accéder directement à
n'importe quelle adresse mémoire.

Corollaires :
- Accès à la mémoire VGA (0xB8000)
- Accès aux registres mémoire-mappés
- Accès aux tables de pages (CR3)
- Utilisation de pointeurs vers des adresses fixes

AXIOME FS4 : GESTION MANUELLE DE LA MEMOIRE
-------------------------------------------
Principe : En mode freestanding, il faut implémenter soi-même les algorithmes
d'allocation de mémoire.

Algorithmes courants :
- Bitmap allocation
- Buddy system
- Slab allocation
- Linked list allocation

AXIOME FS5 : INTERRUPTIONS ET EXCEPTIONS
----------------------------------------
Principe : En mode freestanding, il faut gérer les interruptions matérielles
et les exceptions du processeur.

Étapes :
1. Initialiser la GDT (Global Descriptor Table)
2. Initialiser l'IDT (Interrupt Descriptor Table)
3. Configurer le PIC (Programmable Interrupt Controller)
4. Écrire les gestionnaires d'interruptions (ISR)
5. Activer les interruptions (sti)

================================================================================
PARTIE 5 : BONNES PRATIQUES
================================================================================

BP1 : VALIDEZ TOUS LES POINTEURS
--------------------------------
Principe : Toujours vérifier que les pointeurs ne sont pas NULL avant de les
déréférencer.

BP2 : INITIALISEZ TOUTES LES VARIABLES
--------------------------------------
Principe : Les variables non initialisées contiennent des valeurs indéfinies.

BP3 : LIBEREZ LA MEMOIRE ALLOUEE
--------------------------------
Principe : Toujours libérer la mémoire allouée dynamiquement avec free().

BP4 : UTILISEZ DES CONSTANTES AU LIEU DE MAGIC NUMBERS
------------------------------------------------------
Principe : Les nombres magiques réduisent la lisibilité et la maintenabilité.

BP5 : DOCUMENTEZ LE CODE
------------------------
Principe : Les commentaires expliquent le "pourquoi", pas le "quoi".

BP6 : EVITEZ LE COMPORTEMENT INDEFINIE
--------------------------------------
Principe : Le comportement indéfini est la source de bugs les plus dangereux.

BP7 : TESTEZ TOUS LES CAS D'ERREUR
----------------------------------
Principe : Les fonctions peuvent échouer (malloc renvoie NULL, etc.).

BP8 : UTILISEZ LES WARNINGS DU COMPILATEUR
------------------------------------------
Principe : -Wall -Wextra -Wpedantic détectent de nombreux bugs potentiels.

BP9 : SEPAREZ LES DECLARATIONS DES INCLUSIONS
---------------------------------------------
Principe : Les fichiers .h doivent contenir uniquement des déclarations.

BP10 : UTILISEZ DES GUARDS DANS LES HEADERS
-------------------------------------------
Principe : Empêche les inclusions multiples d'un même fichier header.

Exemple :
#ifndef MY_HEADER_H
#define MY_HEADER_H
// Contenu du header
#endif

BP11 : UTILISEZ restrict POUR LES FONCTIONS D'ALLOCATION
---------------------------------------------------------
Principe : Améliore les optimisations du compilateur.

BP12 : EVITEZ LES CASTS DE POINTEURS ENTRE TYPES DIFFERENTS
-----------------------------------------------------------
Principe : Risque de violation de la règle du strict aliasing.

BP13 : UTILISEZ LES UNIONS POUR L'ACCES MEMOIRE TYPE-SAFE
---------------------------------------------------------
Principe : Les unions sont autorisées par la règle du strict aliasing.

Exemple :
union register32 {
    uint32_t value;
    uint8_t bytes[4];
};

union register32 reg;
reg.value = 0x12345678;
uint8_t low_byte = reg.bytes[0]; // OK

PARTIE 6 : PORTABILITE
================================================================================

P1 : LA TAILLE DES TYPES EST IMPLEMENTATION-DEFINIE
---------------------------------------------------
Principe : Le standard C ne définit pas la taille exacte des types de base.

Garanties minimales :
- sizeof(char) == 1 (seule garantie)
- sizeof(short) >= sizeof(char)
- sizeof(int) >= sizeof(short)
- sizeof(long) >= sizeof(int)
- sizeof(long long) >= sizeof(long)

P2 : L'ORDRE DES OCTETS EST IMPLEMENTATION-DEFINIE
--------------------------------------------------
Principe : Le standard C ne spécifie pas l'ordre des octets dans une valeur
multi-octets (endianness).

Corollaires :
- Little-endian : octet le moins significatif en premier (x86, ARM)
- Big-endian : octet le plus significatif en premier (SPARC, PowerPC)
- Utiliser des fonctions de conversion pour les données réseau

P3 : LA MEMOIRE EST BYTE-ADDRESSABLE
------------------------------------
Principe : Chaque octet de mémoire a une adresse unique.

Corollaires :
- Un pointeur char peut pointer vers n'importe quel octet
- sizeof(char) == 1 (par définition)

P4 : LES LIMITES DES TYPES SONT DEFINIES DANS <limits.h>
--------------------------------------------------------
Principe : Les valeurs minimales et maximales des types sont définies dans
<limits.h> et <float.h>.

Exemples :
- INT_MAX, INT_MIN pour int
- LONG_MAX, LONG_MIN pour long
- UINT_MAX pour unsigned int
- CHAR_BIT (généralement 8)

PARTIE 7 : VERSIONS DU STANDARD C
================================================================================

C89 / ANSI C (1989)
-------------------
- Premier standard officiel
- 32 mots-clés
- Aucune fonction inline
- Aucune variable déclarée au milieu d'un bloc
- Type void* pour les pointeurs génériques

C99 (1999)
----------
- Variables déclarables n'importe où dans un bloc
- Fonctions inline
- Type long long
- Arrays de taille variable (VLA)
- Flexible array members
- Qualificateur restrict
- _Bool (via stdbool.h)
- Commentaires //
- Compound literals
- Designated initializers

C11 (2011)
----------
- Model memory (sequenced-before)
- _Atomic
- Threads (via threads.h)
- Generic selection (_Generic)
- Alignement (_Alignas, _Alignof)
- static_assert
- remove_extent_t, remove_pointer_t

C17 / C18 (2017/2018)
----------------------
- Corrections de bugs mineurs
- Pas de nouvelles fonctionnalités

C23 (2024)
----------
- nullptr_t (via stddef.h)
- auto pour l'inférence de type (seulement dans les déclarations)
- bool natif (pas besoin de stdbool.h)
- true et false comme mots-clés
- typeof et typeof_unqual
- constexpr
- inline variables
- UTF-8 string literals (u8"")
- remove_cv_t
- __VA_OPT__ pour les macros variadiques
- _BitInt(n) pour les types entiers de taille spécifique

================================================================================
PARTIE 8 : AXIOMES HISTORIQUES ET PHILOSOPHIQUES
================================================================================

H1 : C EST UN LANGAGE DE SYSTEME
--------------------------------
Principe : C a été créé pour écrire le système d'exploitation UNIX.

Corollaires :
- Proche du matériel mais portable
- Contrôle total sur la mémoire
- Performance maximale

H2 : "TRUST THE PROGRAMMER"
---------------------------
Principe : C fait confiance au programmeur, ne impose pas de restrictions
inutiles.

Corollaires :
- Pas de vérification de limites de tableau
- Pas de gestion automatique de mémoire
- Pas de garbage collector
- Le programmeur est responsable de tout

H3 : "KISS" (Keep It Simple, Stupid)
------------------------------------
Principe : C est conçu pour être simple et expressif.

Corollaires :
- Peu de mots-clés (32 dans C89)
- Syntaxe concise
- Pas de fonctionnalités superflues

H4 : PORTABILITE VERSUS CONTROLE
--------------------------------
Principe : C trouve un équilibre entre portabilité et contrôle du matériel.

Corollaires :
- Code standard C est portable sur toutes les plateformes
- Extensions spécifiques (GCC, Microsoft) offrent plus de contrôle
- Mode freestanding pour les cas extrêmes (noyaux)

================================================================================
PARTIE 10 : ERREURS FREQUENTES ET PITFALLS
================================================================================

ERREUR 1 : FORGETTING TO NULL-CHECK POINTERS
--------------------------------------------
Symptôme : Crash ou comportement indéfini
Solution : Toujours vérifier ptr != NULL avant de déréférencer

ERREUR 2 : OFF-BY-ONE ERRORS IN ARRAYS
---------------------------------------
Symptôme : Accès hors limites
Solution : Rappeler que les tableaux commencent à l'indice 0

ERREUR 3 : CONFUSING = AND ==
------------------------------
Symptôme : Affectation au lieu de comparaison
Solution : Écrire const == variable (const first) pour détecter les erreurs

ERREUR 4 : MEMORY LEAKS
-----------------------
Symptôme : Consommation croissante de mémoire
Solution : Toujours appeler free() pour la mémoire allouée

ERREUR 5 : DOUBLE FREE
-----------------------
Symptôme : Crash ou corruption de la heap
Solution : Mettre le pointeur à NULL après free()

ERREUR 6 : USE AFTER FREE
--------------------------
Symptôme : Comportement indéfini
Solution : Ne pas utiliser de pointeurs après free()

ERREUR 7 : VIOLATION DU STRICT ALIASING
---------------------------------------
Symptôme : Optimisations incorrectes du compilateur
Solution : Utiliser des unions ou des pointeurs char*

ERREUR 8 : UNINITIALIZED VARIABLES
----------------------------------
Symptôme : Valeurs aléatoires, comportement indéfini
Solution : Toujours initialiser les variables

ERREUR 9 : INCORRECT STRING TERMINATION
---------------------------------------
Symptôme : Buffer overflow, crash
Solution : Assurer que les chaînes sont terminées par '\0'

ERREUR 10 : STACK OVERFLOW
---------------------------
Symptôme : Crash
Solution : Éviter les fonctions récursives profondes, utiliser la heap pour
           les données volumineuses
